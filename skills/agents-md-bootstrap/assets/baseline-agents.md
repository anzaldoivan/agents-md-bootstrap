# Reusable policy baseline

This asset is an adaptation template, not repository evidence or an instruction file automatically applied by a client. A user-supplied personal baseline replaces these defaults. Preserve applicable policy meaning when adapting it; headings and wording are optional. Omit this introduction from generated instructions. Do not claim these preferences were discovered in code.

## Architecture and workflow

- Preserve user work and stay within the requested task. Inspect relevant implementation and local instructions before editing; surface unresolved consequential conflicts.
- Locate and update the canonical owner of behavior, configuration, and documentation. Respect established architecture and boundaries; prefer the smallest coherent change over unrelated refactors, speculative abstractions, or competing implementations.
- Carry authorized work through implementation and verification. Ask only for missing decisions that materially affect correctness, scope, or authorization; continue independent work while waiting.

## Testing integrity

- Run checks appropriate to changed behavior and add or update meaningful coverage where needed. Test observable behavior and important invariants rather than merely mirroring the implementation.
- Do not weaken valid tests, assertions, checks, or quality gates to make a change pass. Fix the cause; change an obsolete expectation only when the intended behavior justifies it, and explain why.
- Distinguish inspected definitions from executed checks. Report failures and unrun checks honestly; do not claim completion when required work remains.

## Technical writing and documentation

- Use clear, concise technical language: familiar words, consistent terms, active voice, and explicit actions. Apply Simplified Technical English principles where useful without claiming strict standards compliance unless specifically required and verified.
- Update documentation affected by behavior or workflow changes at its canonical source. Explain consequential decisions and limitations; avoid stale copies of facts maintained elsewhere.
- Add comments where they explain non-obvious rationale, constraints, or tradeoffs. Keep them accurate; do not narrate obvious code.

## Generated artifacts and dependencies

- Identify generated and vendored files before editing. Change generated artifacts through their source and established generator, then verify the output; do not hand-edit generated copies or casually modify vendored code.
- Reuse existing dependencies where suitable. Add or upgrade dependencies only when justified by the task; avoid unrelated dependency churn. Use the repository's established package workflow and keep manifests and lockfiles consistent through its tooling, rather than hand-editing resolutions.

## Security and Git hygiene

- Keep credentials, secrets, private data, and machine-specific personal settings out of shared artifacts and logs. Preserve security boundaries and validation; do not bypass protections to make work succeed.
- Inspect status and the complete relevant diff. Preserve unrelated staged, unstaged, and untracked work; do not discard or overwrite it to simplify the task.
- Do not perform destructive Git operations, commit, push, or publish without authorization. When committing is authorized, include only intended changes and review what is staged.

## Tools, skills, and scoped instructions

- Prefer available purpose-built tools and established repository workflows; inspect command effects before running destructive or externally mutating actions. Tool access alone is not authorization.
- Use relevant available specialized skills when they materially help the task, reading their instructions first. Do not assume a particular client, tool, or skill exists.
- Read applicable scoped instructions before editing their paths. Follow known discovery and authority rules; resolve consequential conflicts rather than assuming all clients share precedence.

## Completion

- Verify the result against the request, inspect the diff, and report what changed, why, relevant checks and outcomes, and remaining limitations. Separate completed work from blockers and assumptions.

## Adoption

Use the policy dispositions in [evidence-policy.md](../references/evidence-policy.md). Compress overlapping rules without deleting applicable obligations. Omit a rule only with an accounted-for disposition; lack of existing practice is not a reason to reject an explicit policy preference. Claim coverage elsewhere only after inspecting equivalent wording and confirming applicability. Add repository-specific pointers only after inspecting their targets. Keep the working ledger and adoption rationale in the report, not in permanent instructions.
